Источник: model/01_Elements.md, model/02_Relationships.md, model/05_GapAnalysis.md, model/06_MigrationRoadmap.md

Модель утверждена архитектором (этап 4), gap-анализ (этап 5) и дорожная карта (этап 6) утверждены.

## 1. Общее описание проблемы выбора

В целевой архитектуре RetailPro требуется внедрить платформу единых данных клиентов (CDP, компонент `app_cdp`) для закрытия разрывов GAP-03 (отсутствует единый профиль клиента) и GAP-05 (отсутствует CDP), а также связанные с ней изменения: Customer API (`ai_customer_api`, GAP-06), интеграция POS и интернет-магазина с CDP (GAP-07, отношения R-08, R-09), замена Excel на автоматическую сегментацию (GAP-01, GAP-09).

Ключевые точки принятия решений, выявленные в модели и gap-анализе:

1. **Способ внедрения CDP**: разработка собственного решения (внутренняя разработка) vs покупка готового коммерческого CDP vs облачный CDP (SaaS).
2. **Место Customer API**: внутри CDP (соответствует отношению `Rel_Composition` R-10: `app_cdp` включает `ai_customer_api`) vs отдельный компонент vs шлюз на стороне интеграции.
3. **Подход к интеграции POS и интернет-магазина**: прямые потоки R-08/R-09 (`app_pos` → `app_cdp`, `app_eshop` → `app_cdp`) vs посредник (ESB/iPaaS) vs событийный подход.
4. **Замена Excel**: немедленный переход на автоматическую сегментацию через `app_analytics` / `as_segmentation` vs поэтапный переход (Excel остается на переходный период).

Выбор в каждой точке влияет на состав рабочих пакетов (WP-03, WP-05, WP-06, WP-01), закрываемые gaps (GAP-03, GAP-05, GAP-06, GAP-07, GAP-01, GAP-09) и элементы ядра (`app_cdp`, `ai_customer_api`, `app_pos`, `app_eshop`, `app_excel`, `app_analytics`, `as_segmentation`).

## 2. Альтернативы

### Вариант A: Собственная разработка CDP (внутренняя разработка)

CDP разрабатывается собственными силами команды RetailPro. Customer API реализуется как часть собственного CDP (соответствует R-10). Интеграция POS и интернет-магазина через прямые потоки R-08/R-09. Excel заменяется немедленно после запуска автоматической сегментации.

Закрывает gaps: GAP-03, GAP-05 (CDP), GAP-06 (Customer API), GAP-07 (интеграция POS/интернет-магазин), GAP-01, GAP-09 (автоматическая сегментация, замена Excel).

Меняет пакеты работ: WP-03 (Внедрить CDP) — существенно усложняется (разработка вместо настройки/внедрения готового решения); WP-05 (Создать Customer API) — входит в WP-03 как часть собственного решения; WP-06 (Интегрировать POS и интернет-магазин с CDP) — прямая разработка интеграционных интерфейсов; WP-01 (Автоматизировать сегментацию) — без изменений.

Новые элементы ядра: не появляются (используются элементы из 01_Elements.md: `app_cdp`, `ai_customer_api`, `app_analytics`, `as_segmentation`).

### Вариант B: Покупка готового коммерческого CDP (on-premise или установка на своей инфраструктуре)

Приобретается лицензия готового коммерческого CDP, настраивается под процессы RetailPro. Customer API — стандартный интерфейс купленного CDP (в составе CDP, R-10). Интеграция POS и интернет-магазина через прямые потоки R-08/R-09 с использованием стандартных коннекторов CDP. Excel заменяется немедленно.

Закрывает gaps: GAP-03, GAP-05 (CDP), GAP-06 (Customer API), GAP-07 (интеграция POS/интернет-магазин), GAP-01, GAP-09.

Меняет пакеты работ: WP-03 — меняется содержание (закупка, настройка, интеграция готового решения вместо разработки); WP-05 — входит в WP-03 как стандартный интерфейс купленного CDP; WP-06 — используется стандартные коннекторы, объем разработки снижается; WP-01 — без изменений.

Новые элементы ядра: не появляются.

### Вариант C: Облачный CDP (SaaS) + отдельный Customer API + интеграция через посредника (ESB/iPaaS) + поэтапная замена Excel

CDP разворачивается как облачный сервис (SaaS). Customer API выносится за пределы CDP как отдельный компонент (отклонение от R-10, который требует Rel_Composition внутри CDP — требует проверки архитектором). Интеграция POS и интернет-магазина через посредника (ESB/iPaaS) вместо прямых потоков R-08/R-09 (требует пересмотра отношений R-08, R-09 — требует проверки архитектора). Excel остается на переходный период, замена — поэтапная после запуска облачного CDP и посредника.

Закрывает gaps: GAP-03, GAP-05 (CDP), GAP-06 (Customer API — отдельный компонент, отклонение от R-10), GAP-07 (интеграция через посредника, отклонение от R-08/R-09), GAP-01, GAP-09 (поэтапно).

Меняет пакеты работ: WP-03 — развертывание облачного CDP вместо установки/разработки; WP-05 — Customer API как отдельный компонент, не в составе CDP (требует пересмотра R-10); WP-06 — интеграция через посредника (ESB/iPaaS), новые зависимости; WP-01 — поэтапный переход, Excel сохраняется промежуточно.

Новые элементы ядра: не объявляются (используются элементы из 01_Elements.md), но отношение R-10 (CDP включает Customer API) и R-08/R-09 (прямые потоки) требуют пересмотра — требует проверки архитектора.

## 6. Риски и допущения

### Риски

- **Вариант A**: высокая сложность разработки CDP с нуля; риск задержек критического пути (WP-04 → WP-03 → WP-06 → WP-07 → WP-01 → WP-02); механизм учета согласий разрабатывается с нуля (правовой риск до отработки WP-04).
- **Вариант B**: зависимость от вендора коммерческого CDP (лицензирование, поддержка, выход из поддержки); риск неполного соответствия требованиям без кастомизации; правовые риски при обработке данных в solution вендора.
- **Вариант C**: высокая зависимость от облачного вендора CDP и вендора посредника (ESB/iPaaS); отклонение от отношений R-10 (Customer API не в составе CDP) и R-08/R-09 (прямые потоки) требует пересмотра модели и проверки архитектора; дополнительные правовые риски при хранении данных клиентов в облаке; сложность синхронизации между облачным CDP, посредником и локальными системами.

### Допущения

- Сроки, бюджет и трудозатраты не оценены — в документах отсутствуют (этап 6, раздел 9).
- Исполнители технических пакетов (WP-03, WP-05, WP-06, WP-07) не заданы в модели (этап 6, раздел 10).
- Все требования `req_*` выведены неявно из `input/retailpro_case.md`, в `01_Elements.md` нет элементов `Motivation_Requirement` — требует проверки архитектора (этап 5, раздел 4; этап 6, раздел 10).
- Неявный технологический gap (инфраструктура для CDP) не оформлен в модели этапа 5 — требует проверки архитектора (этап 5, раздел 4; этап 6, раздел 10).
- Порядок фаз (данные и согласия → CDP → интеграция → аналитика и персонализация) соответствует правилам навыка, но не явно зафиксирован в источнике (этап 6, раздел 10).
- Классификация `app_excel` как `Application_Component` неточна (уверенность low) — влияет на GAP-09 и WP-01 (этап 5, раздел 4; этап 6, раздел 10).

## 7. Рекомендация

Предпочтительным представляется **Вариант B (покупка готового коммерческого CDP)** с сохранением отношений модели: Customer API в составе CDP (R-10), прямые потоки POS и интернет-магазина в CDP (R-08, R-09), немедленная замена Excel на автоматическую сегментацию.

Обоснование:
- Полное соответствие утвержденным отношениям модели (R-10, R-08, R-09) без необходимости пересмотра `01_Elements.md` и `02_Relationships.md`;
- Все gaps GAP-01…GAP-10 закрываются утвержденными пакетами работ WP-03…WP-07 без изменения состава плато;
- Низкая зависимость от разработки с нуля по сравнению с Вариантом А;
- Ниже правовые и архитектурные риски по сравнению с Вариантом C (данные остаются под контролем компании, отношения модели не изменяются).

Условия, при которых вариант перестает быть лучшим:
- Если готовый коммерческий CDP не может обеспечить учет согласий клиентов (GAP-04, GAP-10) — потребуется доработка или возврат к Варианту А;
- Если лицензирование готового CDP неприемлемо по цене или условиям — данные отсутствуют в модели, требует проверки архитектором;
- Если бизнес требует облачного развертывания по стратегическим причинам — возможен переход к Варианту C с пересмотром отношений R-10, R-08, R-09.

**Решение принимает архитектор.**

## 8. Связь с gap-анализом и дорожной картой

- **Gaps**: выбор альтернативы напрямую влияет на закрытие GAP-03, GAP-05 (CDP), GAP-06 (Customer API), GAP-07 (интеграция POS/интернет-магазин), GAP-01, GAP-09 (автоматическая сегментация и замена Excel). Все остальные gaps (GAP-02, GAP-04, GAP-08, GAP-10) закрываются независимо от выбора способа внедрения CDP.
- **Пакеты работ**: WP-03 (Внедрить CDP), WP-05 (Создать Customer API), WP-06 (Интегрировать POS и интернет-магазин с CDP), WP-01 (Автоматизировать сегментацию) меняют содержание и сложность в зависимости от варианта. WP-04 (Синхронизировать согласия клиентов) и WP-07 (Внедрить аналитическую платформу) и WP-02 (Внедрить сервис персональных предложений) не зависят от выбора альтернативы CDP.
- **Плато**: Варианты A и B не меняют состав плато PL-01…PL-04 из утвержденной дорожной карты. Вариант C требует пересмотра состава Transition 1 (отдельный Customer API, посредник) и порядка поэтапной замены Excel.
- **Критический путь** (WP-04 → WP-03 → WP-06 → WP-07 → WP-01 → WP-02) сохраняется для вариантов A и B; для варианта C возможны изменения из-за зависимости от посредника и облачного вендора.

## 9. Спорные решения (требует проверки архитектором)

1. Все требования `req_*` (req_unified_profile, req_consent, req_customer_api, req_data_integration, req_auto_segmentation) выведены неявно из `input/retailpro_case.md`; в `01_Elements.md` нет элементов `Motivation_Requirement` (префикс `req_`). Каждый gap этапа 5 помечен "требует проверки архитектором". Сравнение альтернатив наследует это ограничение.
2. Вариант C отклоняется от отношения R-10 (`Rel_Composition`: CDP включает Customer API) — Customer API выносится как отдельный компонент. Требует пересмотра `02_Relationships.md` и проверки архитектора.
3. Вариант C отклоняется от отношений R-08/R-09 (`Rel_Flow`: прямые потоки POS → CDP, интернет-магазин → CDP) — интеграция через посредника (ESB/iPaaS). Требует пересмотра `02_Relationships.md` и проверки архитектора.
4. Вариант C предполагает поэтапную замену Excel (GAP-09), что меняет порядок WP-01 и состав плато Transition 1 → Target. Требует утверждения архитектора.
5. Классификация `app_excel` как `Application_Component` имеет уверенность low в `01_Elements.md` (может быть инструментом конечного пользователя). Влияет на GAP-09 и WP-01 во всех вариантах.
6. Слой Technology пуст — технологические элементы и инфраструктура для CDP не описаны. Неявный технологический gap не оформлен (этап 5), требует проверки архитектора.
7. Исполнители для WP-03, WP-05, WP-06, WP-07 не заданы в модели (указаны как "не определена в 01_Elements.md").
8. Оценка стоимости и сроков отсутствует ("не оценено") — рекомендация сделана без количественных данных, требует подтверждения архитектором после получения оценок.
9. Выбор варианта (рекомендация Вариант B) не является итоговым решением; финальное решение принимает архитектор.
